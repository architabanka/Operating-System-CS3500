2.1 
- size (200000): Total number of blocks in the entire disk image. Set by mkfs to FSSIZE. Used by the kernel to check valid block bounds across disk operations.
- nblocks (199328): Number of data blocks available for file storage. Set by mkfs by subtracting all metadata/overhead blocks (boot block, superblock, log, inodes, bitmap, refcounts) from total size. Used by balloc() to bound data block allocation searches.
- ninodes (200): Total number of inodes in the file system table. Set by mkfs to NINODES. Used by ialloc() and iget() to bound inode array searches.
- nlog (241): Number of blocks reserved for the transaction log. Set by mkfs to LOGSIZE + 1 (header + log blocks). Used by log.c (initlog()) to allocate and manage transaction logging.
- logstart (2): Starting block number of the transaction log (located immediately after boot block 0 and superblock 1). Set by mkfs. Used by initlog() to locate the log on disk.
- inodestart (243): Starting block number of the on-disk inode table (logstart + nlog = 2 + 241 = 243). Set by mkfs. Used by the IBLOCK() macro in kernel/fs.h to compute the disk block containing a given inode number.
- bmapstart (256): Starting block number of the free-block bitmap. Set by mkfs (immediately following the inode blocks). Used by the BBLOCK() macro in kernel/fs.h to locate bitmap blocks during balloc() and bfree().
- refstart (281): Starting block number of the block reference count area. Set by mkfs (following the bitmap area). Used by reference-counting routines managing disk block sharing.
The kernel reads the superblock in readsb() located in kernel/fs.c during file system initialization (called via iinit()). readsb() calls bread(dev, 1) to read block 1 (the superblock) from disk into memory.

4.3 Increasing BSIZE to 4096 bytes reduces the pointer overhead fraction from ~0.3906% to ~0.0977% (roughly a 4x decrease in relative metadata overhead). 
Because each 4 KB block can hold 4 times as many pointers (1024 vs 256), fewer pointer blocks are required to address a significantly larger number of data blocks.

5.
5.1 holding a symlink's inode lock while resolving its target pathname via namei() can lead to deadlocks. If a symlink points to itself or if two symlinks point to each other in a loop (A -> B, B -> A) 
attempting to acquire the lock of the next symlink or re-acquire the lock of an already locked inode in the chain will cause a thread to block on a lock, it or a concurrent caller holds, deadlocking the system. 
Also holding locks across pathname traversals blocks concurrent file system operations on those inodes.

My implementation reads and validates the target string from the symlink inode into a local buffer and then releases the symlink's inode lock using iunlockput(ip) before calling namei() to look up the target path. 

5.2 a) when opening 'a/first' (which stores '../b/second'), the containing directory of 'first' is 'a/'. The relative target '../b/second' is appended to 'a/', forming the combined path 'a/../b/second'. 
'namei()' looks up this path starting from the root directory '/', resolving 'a/..' to root '/', then entering directory 'b/'.
b) The lookup resolves to 'b/second', which is a symlink storing 'file'. The containing directory of 'second' is 'b/'. The relative target 'file' is appended to 'b/', forming 'b/file'. 
'namei()' resolves 'b/file', which points to the final file.
